# UC-M2-12 — Generate SPED Contribuições (`GenerateSpedContribuicoesUseCase`)

**Module:** M2 — Fiscal: NFe ([module spec](../m2-fiscal-nfe.md))
**Context package:** `br.gravita.tax`
**Roadmap phase:** Phase 7 — Visibilidade (doc §14)

## Functional requirement

§3.4: "SPED Contribuições: EFD PIS/COFINS file generation; assessed per period."

## Description

Triggered by a user (typically the accountant or an admin) requesting the EFD PIS/COFINS file for a given company and period. Reads every `NfeDocument` and `InboundNfe` in the period, assesses PIS/COFINS per the company's tax regime, and generates the TXT file in the EFD Contribuições layout.

## Port signature

```java
public interface GenerateSpedContribuicoesUseCase {
    SpedContribuicoesFile execute(GenerateSpedContribuicoesCommand command);
}
```

`GenerateSpedContribuicoesCommand` fields: `companyId`, `period`. Returns a `SpedContribuicoesFile` (TXT content + assessment summary).

## Outbound ports required

- `NfeRepositoryPort`, `InboundNfeRepositoryPort` — source records for the period.
- `GenerateSpedFilePort` — shared with [UC-M2-11](uc-11-generate-sped-fiscal.md).

## REST endpoint

`POST /api/sped/contribuicoes`

## Domain entities touched

- Reads `NfeDocument`, `InboundNfe` — writes no new aggregate, only the generated file.

## Acceptance criteria

- [ ] Assesses PIS/COFINS per period, using the company's tax regime.
- [ ] Covers every authorized `NfeDocument` and confirmed `InboundNfe` in the period.
- [ ] Output matches the EFD Contribuições TXT layout.

## Implementation notes

- **Endpoint.** `POST /api/sped/contribuicoes` with `{"companyId": "<uuid>", "period": "yyyy-MM"}`. `200` with `companyId`, `period`, `fileName`, the `assessment` summary and `txt`, the file's bytes (ISO-8859-1, CR LF, as the SPED validator reads it) in base64. Errors: `400` missing/malformed `companyId` or `period`; `404` unknown company; `409` the company is under the Simples Nacional. Like the other `tax` endpoints it is not gated by a screen permission.
- **Period and coverage (AC2).** A calendar month in the server's time zone. Every `AUTHORIZED` `NfeDocument` the company issued, by the day SEFAZ authorized it, and every `CONFIRMED` `InboundNfe`, by the day its supplier issued it (pending-conference, cancelled and rejected documents are not booked). Sales are the NFe issued under an exit CFOP (5/6/7); an NFe the company issued under an entry CFOP (1/2/3) is a purchase of its own, as in the fiscal books (UC-M2-13).
- **Regime (AC1).** *Lucro Real* is non-cumulative (general rates PIS 1.65% / COFINS 7.60%, credits on purchases); *Lucro Presumido* is cumulative (0.65% / 3.00%, no credits). *Simples Nacional* pays PIS/COFINS inside its DAS and does not file the EFD Contribuições, so the request is refused (`409`) rather than answered with an empty file.
- **How a sale is levied.** As the NFe states it: the base, rate and amount of the item's PIS/COFINS line, so the assessment reconciles with what was invoiced. An item with no such line (or a zero one) bears nothing (CST `49`); one at the regime's general rate is CST `01`, at any other CST `02`. Sales are grouped by rate for `M210`/`M610` (`COD_CONT` `01`/`02` non-cumulative, `51`/`52` cumulative).
- **How a purchase earns a credit (non-cumulative only).** When its CFOP says it is for resale (`x102`, `x403`, `x405`) or an input (`x101`, `x401`), **and** the supplier's NFe itself bore the contribution (so zero-rated, suspended and monophasic purchases earn none). The credit is the item's value at the *buyer's* general rate, not the supplier's stated amount (which depends on the supplier's own regime). CST `50`; every other purchase is CST `70`. The credit is set against the contribution up to its amount; the excess is carried forward (`SLD_CRED`), never refunded. The `NAT_BC_CRED` is `01` (resale) or `02` (input).
- **Assessment summary.** Per contribution: `revenue`, `base`, `contribution`, `credit`, `creditUsed`, `creditBalance`, `payable` (`contribution - creditUsed`). It is computed from the same items the `C170` registers are written from, so the summary, Block C and Block M cannot disagree.
- **Layout (AC3).** Registers follow the RFB "Guia Prático" field order: `0000`, `0110`, `0140`, `0150`, `0190`, `0200` (Block 0); `C010`, `C100`, `C170` (Block C, itemized bookkeeping); `M100`/`M105`, `M200`/`M210`, `M500`/`M505`, `M600`/`M610` (Block M); Blocks A, D, F, I, P and 1 are written empty. `X001`, `X990` and Block 9 are generated by the file writer from the registers actually written.
- **Shared port.** `GenerateSpedFilePort` (adapter `SpedFileAdapter`) writes the physical shape both EFDs share: `|REG|f1|f2|`, CR LF, ISO-8859-1, the `X001`/`X990` pair of every block and Block 9 with its `9900` counters. The use case supplies only its registers; UC-M2-11 should build its own registers and call the same port rather than add a second writer. A field is a `String`, `BigDecimal` (written with a comma, at its own scale), `LocalDate` (`ddMMyyyy`), another `Number`, or `null` for an empty field.
- **Known gaps - the file is not yet ready to submit as is.** It has not been run through the RFB's PVA validator, and the following are assumptions or are left empty:
  - `NOME` (`0000`, `0140`) and `COD_MUN` (`0000`, `0140`, `0150`) are empty: the `Company` aggregate holds neither a legal name nor an IBGE municipality code. Participants' address fields are empty for the same reason.
  - `COD_VER` is `006`; confirm against the layout version the RFB currently requires.
  - CSTs are derived (the domain holds none): `01`/`02`/`49` on sales, `50`/`70` on purchases. `IND_NAT_PJ` is always `00`; `IND_ATIV` comes from the CNAE division (`0` industrial, `2` trade, `9` other); `TIPO_ITEM` is `99`; `IND_PGTO`/`IND_FRT` are `9`; credits are appropriated directly (`IND_APRO_CRED` `1`).
  - Not generated: `0100` (accountant), `M400`/`M410` (untaxed revenue), `M110`/`M115` (credit adjustments), and any adjustment, deferral or withholding of the period.
